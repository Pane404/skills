### L3-18 感知性能（Perceived Performance）

- 判断句：先量延迟带再选载体 —— <100ms 无 UI、100–400ms 即时确认、400ms–1s 加载指示、>2s 给进度、>10s 给 ETA+取消；Doherty 400ms（即时确认）、NN/g 0.1/1/10s、项目 >2s 是不同粒度，不调和成一个数字；感知技巧只改善感受、须先修真实速度。
- 用：搜索/筛选/tab 超 400ms 先 100ms 内确认点击再给即时反馈、内容型首屏用 Skeleton 占位防 CLS、点赞等高频可逆操作用乐观 UI 把 200–800ms 往返藏后台——因越过阈值用户开始「意识到在等」，需维持交互动量。
- 不用：① <400ms 完成还显示 spinner、为「有反馈」加 200ms 人为延迟、假进度条/永恒 99% → 什么都不显示或仅按压态 / 即时响应 / determinate 真实比例（替代）；② 用感知技巧掩盖慢后端、为提速牺牲可达性 → 先做缓存/流式/查询等真实优化 / 保留 inline 冗余与 reduced-motion 静态降级（替代）。
- 必检：感知延迟阈值属保留分歧，须列各方不调和：Doherty 100–400ms（IBM 1982，C）/ NN/g 0.1·1·10s 三限（C）/ 项目 >2s 进度·>10s 取消·<300ms 不显示加载态（D）；分带 0–100/100–400/400ms–1s/1s+/10s+ 各管一级（C/D）。
  用 RUM 的 P75/P90（非中位数/开发机合成）设预算并覆盖最高频微交互（B/D）；autocomplete ≤300ms 出首条、搜索 400ms 前开始出现（D）；阈值只针对感知等待、不砍刻意动效（B）；自动消失消息须 inline 冗余、Skeleton 单一 polite status 播报按 HR-10，焦点不重置 body 按 HR-04、对比按 HR-02。
