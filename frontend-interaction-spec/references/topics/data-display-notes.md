> 按「表格 / 卡片 / 图表 / 列表 → 判断 → 不用+替代 → 检查要点」组织；只讲选型，不讲图表库实现。

### L6-01 table
- 判断：当「行与列都携带含义、且用户要沿列比较数值」时，用原生语义表格把结构化数据呈现为可扫描、可朗读、可导出的网格。
- 不用：只想做页面多列排版、侧栏 + 主内容对齐 → 改用 CSS Grid / Flexbox（L0-07 布局栅格）；`<table>` 做布局会破坏响应式与语义
- 必检：检查表格由原生 `<table>/<thead>/<tbody>/<th>` 构成，且每个 `<th>` 带 `scope`，表头无空单元格。
### L6-02 data-grid
- 判断：把「需要单元格级键盘导航或逐格编辑的结构化数据」变成一个类电子表格的应用型复合组件；仅有排序、筛选、分页或万级只读数据时，普通表格 + 分页/虚拟滚动即可，不因此升级为网格。
- 不用：只有排序 / 筛选 / 分页或万级只读需求，没有单元格级导航与逐格编辑 → 改用 L6-01 表格；少于 5 行的简单数据（如「3 个团队成员」） → 改用 L6-01 表格 或普通列表；网格的排序/选择控件在几行数据上全是噪音（thepace 明确 Don't）
- 必检：检查网格用 `role="grid"`（或原生表）实现，`aria-sort` 在列头、`aria-selected` 在行、半选用原生 `indeterminate`。
### L6-03 list-resource-list
- 判断：把一组结构重复的同类资源垂直排列，让用户「快速扫读 → 找到某一个 → 对它采取行动或进入详情」，是详情页的摘要与导航层级的中继站。
- 不用：用户要逐字段比较数值、找「哪一列最大」 → 改用 L6-01 表格；列表在跨记录比较上只能给「一般」，眼睛要跳跃（Setproduct 决策表）
- 必检：检查列表用 `<ul>/<li>` 语义，标题、负责人、日期、状态在每项处于固定位置，节奏一致。
### L6-04 card
- 判断：把「围绕单一主题的内容与动作」装进一个有边界、可扫描、可独立移动或删除的自包含容器，让每个对象以完整身份被浏览与决策。
- 不用：用户要逐字段比较数值、找「哪个最便宜 / 退款率最高」 → 改用 L6-01 表格；NN/g 指出卡片结构逐项变化、比较困难，且隐藏排序与排名
- 必检：检查每张卡片围绕单一主题，内容按 Image → Title → Description → Action 建立清晰主次层级。
### L6-05 card-grid
- 判断：让「一批彼此对等、地位相同的对象」以等宽卡片按可用空间自动换行铺开，用统一的视觉节拍支持快速视觉浏览、轻比较与批量选择。
- 不用：内容有明确主次、要突出一个主角（新品主推、核心指标） → 改用 L6-06 bento-layout（故意不等大）或 hero + grid 组合；等尺寸会抹平重要性
- 必检：检查卡片等宽、同行等高，标题固定截断、图片统一 `aspect-ratio`，长标题不会抬高整行。
### L6-06 bento-layout
- 判断：用**不等大的格子与跨度**把一组策展过的信息按重要性排成 mosaic，让「尺寸与位置」替用户回答「先看哪个」，是一种信息组织与视觉权重分配决策。
- 不用：长文、博客正文、新闻、法律条款等需要连续线性阅读的内容 → 改用单列正文 + 标题段落（L8-10 详情页）；scriptwalker 明确「便当格会把本该线性的叙事切得支离破碎」
- 必检：检查已先列出内容清单并排出优先级，最大格给了最重要的信息，尺寸差异由重要性而非外观决定。
### L6-07 descriptions-list
- 判断：用原生 `<dl>/<dt>/<dd>` 把「名称 / 术语 → 它的说明或值」显式配成一组，让键值对关系在换样式、缩放、换读屏时都不丢失语义。
- 不用：一组同类、结构重复的对象（订单列表、成员清单） → 改用 L6-03 列表（`<ul>/<ol>`）；`<dl>` 表达的是映射而非集合
- 必检：检查使用原生 `<dl>/<dt>/<dd>`，每个 `<dt>` 非空且至少跟一个 `<dd>`，`<dd>` 紧随其 `<dt>`。
### L6-08 statistic-kpi
- 判断：把**一个**关键指标用大字号、环比/同比变化、迷你趋势线与对比周期压缩成一张卡，让决策者在几秒内判断「好不好、要不要下钻」。
- 不用：一个**没有对比周期**的静态数字（「服务器数量：12」） → 改用 L6-04 卡片 的 statistic 修饰 / L6-07 描述列表；NDS 明确 Metric 必须带比较期
- 必检：检查每张卡只放一个指标，且带趋势方向（箭头 + % 变化）与明确的对比周期标签。
### L6-09 chart
- 判断：把数据编码到「位置 / 长度 / 角度 / 面积 / 颜色」这些视觉通道上，去回答**一个**具体问题；选图的第一原则是「先问要看出什么关系」，而不是「手头有什么数据」。
- 不用：类别超过 7 个、或数值彼此接近需要精确比较时仍用饼图 → 改用**按值排序的条形图**（CleanChart Mistake #1 / probably.dev）；饼图仅用于 3–7 类「部分—整体」
- 必检：检查已先写下这张图要回答的一个问题，并按「比较 / 趋势 / 占比 / 分布 / 关系 / 二维模式」选定图形。
### L6-10 dashboard-layout
- 判断：把一屏组织成「结果指标 → 趋势 → 驱动因子 → 明细下钻」的决策界面，用信息层级、刷新节奏与降噪规则，让反复使用的人在几秒内判断「有没有问题、要不要下钻」。
- 不用：一次性、固定时点、供阅读与归档的静态报告 / 董事会快照 → 改用报表 + PDF/图片导出；helion360 明确「report 为阅读排版，dashboard 为反复自助决策」
- 必检：检查信息层级为「结果 KPI → 趋势 → 驱动因子 → 明细下钻」，并用位置 + 字号 + 颜色构成 KPI 层级金字塔，北极星在左上黄金区。
### L6-11 timeline
- 判断：把**策展过的事件序列**沿一条脊线按正向顺序挂起来，让用户重建「先发生什么、再发生什么、因此下一步为何推迟」的过程形状。
- 不用：项目排程、任务依赖、关键路径、拖拽改期 → 改用 Gantt 图 / 排程组件（hex-core 明确 Don't，ancoleman 决策框架中 Project Planning → Gantt Chart）
- 必检：检查时间轴渲染为 `<ol>` 有序列表并带 `aria-label`，事件最旧在前、每条都有时间锚点。
### L6-12 activity-feed
- 判断：把系统自动记录、最新在前的事件，按「谁 + 对什么 + 做了什么」组织成可过滤、可分组、可实时插入的倒序流，让用户不逐个打开对象就能追上近况。
- 不用：需要**穷尽、不可变、可搜索导出**的合规取证（含 IP / 保留策略 / 完整 actor） → 改用 Audit Log；vocab.design / uxpatternsguide 明确 feed 不是证据，弱实现反例正是「分析师导出 feed 期待审计证明却没有 immutable event ID、IP、retention」
- 必检：检查每条写成完整「actor + verb + object」句子，且含 source / channel / timestamp / preview / type / read 状态 / 稳定 destination。
### L6-13 calendar-view
- 判断：把基于时间的信息铺进「日 / 周 / 月」网格，让人一眼比较多个日期与时段、判断可用性与冲突，用于排程与预订而非单纯选一个日期。
- 不用：用户只需要一两个值、不需要完整网格 → 改用简单视图 / L6-08 KPI 卡；skillselion 明确「Use a simpler view when users only need one or two values」
- 必检：检查已按用户角色选定默认视图（诊所日 / 活动预订月），并提供日/周/月/时间线切换且易于切换。
### L6-14 tree
- 判断：让层级数据以**单一 Tab 停靠点 + 方向键**在原地展开/折叠，读者始终同时看得见父、兄弟与新展开的子节点，从而保持「层级的形状」可读。
- 不用：数据是扁平的、只有一层、或主要用于页面间导航 → 改用 L6-03 列表 / L5-11 导航菜单；positioniseverything 明确「flat / one level / mainly navigation → list, disclosure, or nav menu」
- 必检：检查容器 `role="tree"` 且有名称，节点 `role="treeitem"`、子组 `role="group"`，多选带 `aria-multiselectable="true"`。
### L6-15 carousel
- 判断：在一块紧凑区域里**顺序**展示一组 slide，用上一张/下一张控件把内容轮换进视图；它是最需要无障碍纪律的组件之一——必须先给用户「停止」的权力，再谈动效。
- 不用：自动轮换内容里含文本密集、表单、同意 / 法律 / 资格、警告、结算等任务关键内容 → **禁用 auto-advance**，改为静态呈现；uxpatternsguide 明确「Disable auto-advance for text-heavy, task-critical, form, consent, legal, eligibility, warning, checkout
- 必检：检查自动轮换提供**可见 Pause/Play 按钮**，且它是容器内第一个可聚焦元素、位于轮换内容之前。
### L6-16 image-gallery
- 判断：把一组**已可见、可自由点选**的媒体缩略图铺成可扫描的集合，让用户在比较与浏览中挑一张，再按需放大查看大图与元数据。
- 不用：只呈现一张内容图 → 改用 L1-15 宽高比容器 包裹的单图 Image
- 必检：检查每个 `<img>` 都有 alt：有意义图写目的/内容、装饰图 `alt=""`、链接缩略图描述「点开会做什么」。
### L6-17 avatar-group
- 判断：用**重叠的头像堆叠 + 一个「+N」计数**在空间受限处一眼表达「这个对象关联了好几个人」，并把隐藏成员的姓名保留在可访问的展开入口里。
- 不用：只有一个人 → 改用单个 L1-11 Avatar；kanso「Don't show groups of 1. A single avatar is just… an avatar」
- 必检：检查设定 `max` 且超过上限一律显示 `+N` chip，没有静默截断、没有无上限的长串头像。
### L6-18 comment-thread
- 判断：围绕一篇内容或一个对象组织**有作者、有层级、有审核状态**的讨论，让回复始终挂在它所回应的那条评论上，同时把 moderation 与恢复路径设计进模式本身。
- 不用：社交 / 互动机制不创造真实用户价值（无意义的点赞计数） → 去掉该机制；skillselion / uxpatterns.dev 明确「Avoid social or engagement mechanics when they do not create real user value」
- 必检：检查每条评论用 article 类语义容器，含 author、timestamp、content region、具名 action controls。
### L6-19 kanban-board
- 判断：用**列 = 工作流状态**把在制品可视化，让卡片随状态变更在列间移动，从而平衡流动、暴露阻塞与瓶颈——列的位置必须真的改变状态字段。
- 不用：列只是**装饰性分类**、移动卡片并不改变工作流状态（情绪板 / 任意分组） → 不要用看板；uxpatternsguide「Do not use Kanban board for arbitrary categories, mood boards, or dashboards where column movement has no workflow meaning」；改用 L6-01 表格 + 分组状态列，或独立待办列表。
- 必检：检查每列对应真实工作流状态，拖卡到列会更新 status 字段并显示目标状态；没有装饰性分类列。
### L6-20 map
- 判断：把数据放在**物理位置关系**里呈现，回答「在哪里、离多近、哪一片密集」，并始终配一份可读、可键盘操作的等价列表——地图负责空间，列表负责浏览。
- 不用：用户只需要比较名称 / 距离 / 价格，不需要空间关系 → 改用 L6-03 列表 或 L6-01 表格；NSW「Do not rely on users being able to use a map. Make the content available without using the map」
- 必检：检查只在需要看相对位置 / 空间关系时用地图，小屏已评估价值，并提供不依赖地图的文本 / 列表替代。
### L6-21 code-block
- 判断：用等宽、保留空白的 `<pre><code>` 呈现完整代码片段，配一个**常驻、只复制代码本身、反馈可播报**的复制按钮，让读者准确读、准确抄。
- 不用：句子里的标识符 / 函数名引用 → 改用行内 `<code>`（Stellae When NOT to use）
- 必检：检查使用 `<pre><code class="language-*">`，容器 `role="region"` + `aria-label` 含语言，可见语言/文件名标签可程序化关联。
### L6-22 virtualized-list
- 判断：只挂载视口附近的行 + 少量 overscan，用一个高 spacer 保持滚动几何，让万级列表的 DOM 数量恒定；代价是必须显式补偿浏览器 Find、读屏缓冲与焦点连续性。
- 不用：短 / 有界列表（几百行简单行） → 直接普通渲染；GitHub SKILL「Below that, virtualization adds complexity and breaks Ctrl+F, so measure first」、InterviewLane「Virtualizing tiny lists — added complexity without benefit」；先测量再决定。
- 必检：检查按**测量**决定虚拟化：几百行简单行不虚拟化，>1000 项或行重时才启用，未对小列表引入无谓复杂度。

## 跨条目通则

- 选型先问「用户要比较还是浏览」：比较 → 表格；只有单元格级键盘导航或逐格编辑才升级数据网格；浏览 → 列表 / 卡片。
- 行列都携带含义才用表格；每条记录形状不一，改列表或卡片，避免大量空列。
- 普通表格可排序、冻结列、分页，并按测量虚拟化；十万行本身不是升级 Grid 的理由。只有单元格编辑 + 方向键漫游等组合焦点需求 → 数据网格。
- 图表只回答一个问题；多问题拆多图，不堆双轴。
- 空 / 加载 / 错误三态必须出稿，不能只画有数据态。
- 大数字右对齐 + 等宽数字；单位放表头，不在每个单元格重复。
- 排序 / 筛选 / 分页是表格也可具备的能力，不是网格专属；别给静态展示硬塞控件。

## 工程常见但原库未覆盖（外部补充，证据等级 B/D）

> 原库 226 篇聚焦交互模式，下列组件在工程中高频出现但未单列。判据据 MDN / WAI-ARIA APG / 主流设计系统整理，**标注为外部补充，不冒充原库结论**。

### 视频 / 音频播放器
- 判断：内容本身是媒体且需要播放控制 → 播放器；只是封面图 → 图片组件。
- 不用：带声音自动播放；依赖装饰性背景视频传递重要信息。
- 必检：控件键盘可达；有声预录同步媒体提供同步字幕（SC 1.2.2，A；例外为明确标注的文字替代媒体）。预录视频的关键画面信息未由主音轨传达时，AA 还应提供音频描述（SC 1.2.5）。纯音频按 SC 1.2.1 提供等价文字。`HR-03` / `HR-09` / `HR-10`。

### 文件预览（PDF / 图片 / 文档）
- 判断：上传后需要确认内容 → 就地预览；需要编辑 → 进入编辑态。
- 不用：用预览替代下载 / 编辑入口；预览层承载别处拿不到的独家信息。
- 必检：可关闭并归还焦点（C3 / C4）；大文件给加载态；无插件时降级为下载。

### 树形表格（Tree Table）
- 判断：层级与多列属性同时需要比较 → 树形表格；只有层级 → 树；只有属性 → 表格。
- 不用：层级超过 3 层且频繁跨层移动（改主从或搜索），或窄屏移动端；仅「深」或仅「频繁跨层」先按定位成本与替代路径评估，不单独触发切换。
- 必检：展开 / 折叠键盘可操作；`aria-expanded`；层级缩进可读；`HR-04`。

### 甘特图（Gantt）
- 判断：任务有起止时间且要表达依赖 → 甘特图；只看排期 → 日历；只看进度 → 列表 + 进度条。
- 不用：移动端；任务少于 5 条（时间轴更轻）。
- 必检：时间轴可键盘滚动；依赖关系有文字替代；缩放不丢当前视点。

### 二维码 / 水印（QR Code / Watermark）
- 判断：需要跨设备跳转 → 二维码 + 可复制链接；需要标识来源或防截屏 → 水印。
- 不用：二维码作为唯一入口（必须给文字链接）；水印遮挡正文。
- 必检：二维码有文字替代且对比足够（`HR-02`）；水印不影响可读性且可关闭。

### 回到顶部 / 悬浮按钮（Back to Top / Float Button）
- 判断：长页面滚动超过两屏 → 回到顶部；有单一主操作且需常驻 → FAB。
- 不用：短页面；与底部导航或固定操作条重叠。
- 必检：键盘可达；不遮挡内容；滚动方向变化时隐藏；`HR-01`。

### Emoji 选择器（Emoji Picker）
- 判断：表达情绪或轻量反应 → Emoji 选择器；正式表单字段 → 不用。
- 不用：作为唯一输入方式；无搜索的长列表。
- 必检：可键盘浏览；有分类与搜索；选中后焦点回输入框。

## 业务任务模式（能力扩充 v1.2.0 复审修订）

> 用户指定扩充，属过程归纳（证据等级 D），不是原库 226 篇的结论；与上面条目并列使用，不覆盖已裁定基线。

### 查找与批量处理（Saved View / Select All Matching / Bulk Action / Partial Retry）
- 什么时候该想到它：用户反复按同一组条件回到同一批记录，或要对结果集中的多条记录做同一动作。首选「保存筛选为视图 + 跨页选择全部匹配 + 操作前复核范围 + 部分失败仅重试失败项」的工作流；上千条报销一边看票据一边审核、偶尔批量通过时，输出审核工作队列（Work Queue）：左侧筛选，右侧保留当前单据与票据，审核后可继续下一条。
- 哪些条件会改变选型：条件是否需要共享或长期保留（具名视图 vs 临时筛选）；结果集是否跨页且随数据变化（全部匹配 vs 本页）；动作是否不可逆或有外部后果（操作前范围确认 vs 直接执行）；失败能否逐条隔离（失败项重试 vs 整批重跑）。
- 最容易漏掉的行为：跨页全选必须明确「全部匹配 N 条」而不是「本页 N 条」；筛选条件变化后**锁定原选择范围或清空选择并要求重新确认**，不得静默重算换掉用户已选记录；结果分为明确成功、明确失败、**结果未知（响应超时）**三类：超时先查原操作状态或复用原幂等键，确认未执行才进可重试列表，不直接整批重跑；权限失败单独说明原因和处理路径；整批重跑仅在原子回滚已确认或全批幂等时适用；成功结果与失败原因都要保留；批量栏不能遮挡分页与已选数量。
- 用什么场景验收：筛选后 3 页共 240 条报销，其中 7 条权限失败、3 条响应超时但服务端可能已执行、2 条明确网络失败。验收能否保存视图、在第 1 页选全部 240 条、看到影响范围确认；筛选条件变化后原 240 条范围被锁定或清空重选；超时项先显示「结果未知」并查询状态或复用幂等键，不直接入重试队列；仅 2 条明确失败可重试，7 条权限失败单列原因，已执行项不重复产生副作用。
- 流程发送通知：单条、批量、手动或后台触发均可用结果三态。巡检员保存异常照片后若系统自动通知内部维修组，分别显示照片已保存和通知状态。通知响应超时先查原操作状态，或安全地复用原幂等键。权限不足、无效号码或收件人无法定位分别说明原因和处理路径，经修正后按实际发送状态决定是否重试。单条通知按该事件显示结果，批量发送再加影响范围与逐条失败清单。

### 复杂数据呈现（Table / Data Grid / Tree Table / Master–Detail）
- 什么时候该想到它：用户要逐列比较、逐格编辑、保留父子关系，或逐条查看大段详情。默认映射：只读多列比较、排序筛选、万级数据 → 普通表格（分页或虚拟滚动即可）；只有需要单元格级键盘导航或逐格编辑时 → 交互网格（W3C APG Grid 模式）；层级与多列属性同时要比较 → 树形表格；每条有大段详情或附件且要连续处理 → 列表—详情（master–detail，见 `../cards/L7-04.md`）。
- 哪些条件会改变选型：比较维度和是否只读；操作粒度是行、单元格还是节点；**只有单元格级键盘导航或逐格编辑才升级网格，排序/筛选/万级只读本身不是理由**；数据是否有真实父子层级；详情长度与是否需要并排；层级超过 3 层且频繁跨层移动时改主从或搜索，不硬塞树形表格；窄屏主从降级为列表页与详情路由，保留选中状态。
- 最容易漏掉的行为：表格要有 `<th scope>`；网格要支持方向键漫游、`aria-sort` 与半选状态；树形表格要保留展开/折叠状态和层级缩进；主从要有明确空详情态；虚拟化后仍要保证焦点连续与读屏可感知，小数据不无谓虚拟化。
- 用什么场景验收：同一批业务给五个任务——比较 12 列报价、对 1 万条只读订单排序筛选、逐格修改库存、查看组织树及每节点人数、逐条阅读 200 字审核说明；验收能否分别给出表格、表格（不误升级网格）、网格、树形表格、列表—详情，且不互相错配。
