# 页面级与流程模式（C 级专题）

> 目录：L8-01 ｜ L8-02 ｜ L8-03 ｜ L8-04 ｜ L8-05 ｜ L8-06 ｜ L8-07 ｜ L8-08 ｜ L8-09 ｜ L8-10 ｜ L8-11 ｜ L8-12 ｜ L8-13 ｜ L8-14 … ｜ 业务模式：分次办理与提交前复核 ｜ 变化与追溯

> 含 L8 页面级模式 18 条 + L7 渐进披露与容器 11 条；按「判断 → 不用+替代 → 检查要点」组织。

### L8-01 landing-page
- 判断：为单一流量源设计的「一个决策点」页面，把陌生访客在 5 秒内推向唯一一个转化动作，而不是介绍公司。
- 不用：访客目的发散、需要浏览全站品类（如官网入口、老用户随便逛逛） → 用带全局导航与搜索的**首页 / 门户页**；落地页剥离导航会把这类访客困死。
- 必检：用一句话写下本页「唯一目标」与唯一 CTA，并确认页面上不存在第二种主动作。
### L8-02 pricing-page
- 判断：把「已经想买、正在纠结选哪档」的高意向访客，用最小的认知成本推向一个明确且不会后悔的套餐。
- 不用：单一价格、无档位的商品或标准化服务 → 用 L8-10 详情页 直接标价 + 购买按钮；强行做 3 档只会制造假选择。
- 必检：做 5 秒测试：冷访客能说出「我该选哪档」与「它多少钱」，否则先修层级再测别的。
### L8-03 login-auth
- 判断：让已有账号的用户用最少的输入、安全地回到被打断的那个任务，而不是重新认识一次产品。
- 不用：用户还没有账号，需要建立身份 → 用 L8-04 注册与新手引导；把注册折进登录会让两者目标互相干扰。
- 必检：检查全站仅用一条通用失败文案，且「账号不存在 / 密码错 / 账号禁用」三种情况的文案、HTTP 状态码、URL、重定向与响应时长均一致。
### L8-04 signup-onboarding
- 判断：把「刚建好账号、还没体验过产品价值」的用户，在最短路径内送到第一个属于他自己的成功结果，而不是送进一场产品导览。
- 不用：用户只是回来登录已有账号 → 用 L8-03 登录；对回访用户重复欢迎屏与导览是明确的失败模式。
- 必检：写下一个可观测的激活里程碑，并确认流程中每一步都在把它推近，否则删除或后置。
### L8-05 checkout
- 判断：把已经决定要买的顾客，用一条线性、可预测、不被打断的路径送到「订单已确认」，任何多余的决定都在削减成交。
- 不用：想在结算中推 newsletter / 交叉销售 / 限时弹窗 → 用结算**之外**的推荐位或购后邮件；Baymard 明确要求消除 mid-flow interruptions。
- 必检：检查「Guest Checkout」位于账户选择步最顶部、为高对比按钮且视觉权重不低于登录，页首写明「无需注册」。
### L8-06 settings-page
- 判断：让用户带着「我要改某一项」的明确目的进来，能找到、看懂当前值、改完就确信它生效了，且不会误触不可逆操作。
- 不用：一次性提交、改完不长期驻留的信息（联系 / 报名） → 用 L8-18 表单页；设置页是持久配置的家，不是收件箱。
- 必检：检查分组按用户心智 / 影响范围（Personal / Workspace / Company）组织，而非按数据库字段或组织架构。
### L8-07 search-results
- 判断：把「用户刚输入的那个词」变成一组可判断、可收窄、可继续修改的结果，让他尽快确认「找到了没有、还要不要继续找」。
- 不用：用户的首要需求是按类目 / 属性浏览，而非关键词检索 → 用 filtering pattern / 类目陈列页（NSW 设计系统明确区分），别硬套 SERP。
- 必检：检查结果页保留预填当前词的搜索框，并有「找到 N 条关于『X』的结果」摘要行。
### L8-08 no-results
- 判断：当查询返回 0 条时，把「死胡同」改造成一条明确的恢复路径——说明发生了什么，并给出至少三条能继续走下去的路。
- 不用：请求失败 / 网络错误 / 服务不可用 → 用 L3-10 错误状态 + L10-15 错误恢复：重试、保留 query、非搜索路线，不改词。
- 必检：检查已区分「成功 0 条 / 筛选致空 / 请求失败 / 索引待完成 / 权限受限 / 未输入查询」，且各自文案与动作不同。
### L8-09 profile-page
- 判断：既是「别人眼中的身份卡」，也是「本人管理对外展示信息的入口」——让访客几秒内认出这是谁、能做什么，让本人清楚哪些信息对谁可见。
- 不用：管理密码 / 二次验证 / 通知 / 账单 → 用 L8-06 设置页；这些是安全与配置，不是对外身份展示。
- 必检：检查首屏含头像（带 initials 兜底）+ 文本姓名 `h1` + 角色 + 一句简介 + 一个随关系变化的主动作。
### L8-10 detail-page
- 判断：让用户在**不离开这一页**的前提下，把「我大概想要」变成「我完全清楚买到的是什么、可以放心下单」。
- 不用：用户还在比较多个商品 → 用 L8-07 搜索结果页 或 L8-16 功能对比表；详情页只讲一个对象。
- 必检：商品详情示例可含主图 / 图库、价格优惠、评分、规格与唯一「加入购物车」；订单 / 库存等非商品详情只给业务所需字段与操作，不套商品控件。所有详情都需唯一主操作、无竞争 CTA。
### L8-11 error-404-500
- 判断：把「走不通了」变成「还有路可走」——用平实语言说清发生了什么，给出返回 / 搜索 / 重试 / 求助的恢复路径，并让状态码与品牌都保持正确。
- 不用：查询执行成功但 0 条匹配 → 用 L8-08 无结果恢复：改写查询、放宽筛选、返回、搜索、状态说明。
- 必检：检查 404 返回 404（永久删除可用 410）、500 返回 500、维护返回 503 + `Retry-After`，**无一处用 200 承载错误内容**（软 404 反模式项）。
### L8-12 maintenance-page
- 判断：对「事先说好的停机」给出可预期的时间、范围与进度，并用订阅把用户从「反复刷新」变成「收到通知再回来」。
- 不用：未预期的服务端异常 / 500 → 用 L8-11 错误页：承认我方故障 + 重试 + 支持，不要伪装成计划维护。
- 必检：检查维护页返回 **503 + `Retry-After`**，且为不依赖主应用 / 外部 CDN 的静态自包含页面。
### L8-13 multi-step-form
- 判断：把一个太长、带条件或高风险的任务切成几屏「一次一个决策」，同时保证用户随时返回、刷新、隔天回来都不丢任何已填内容。
- 不用：只有 3–5 个相关、低分支的字段 → 用 L8-18 表单页 的单页表单；拆步只会增加点击与放弃（3 题时单页完成率反而更高）。
- 必检：先删除不必要字段，再按主题把剩余拆成 3–5 步，每步一个决策且耗时均衡。
### L8-14 approval-workflow
- 判断：让「需要一串人签字才能推进」的记录在任何时刻都能回答：现在轮到谁、卡了多久、决定依据是什么、谁在何时做了什么——且决定不可被悄悄覆盖。
- 不用：记录没有需要他人做的决定，只是改自己的字段 → 用 L8-10 详情页 / 普通编辑；套审批会凭空加环节。
- 必检：检查仅当「需要他人签字」才使用本模式；纯字段编辑改回详情页；常规小额按例外阈值放行、不路由 3 级签字。
### L8-15 paywall-upgrade
- 判断：在用户**已经尝到价值之后**、正好想再往前一步的那一刻，把「付费」呈现为自然的下一步，而不是任务中途的一座收费站。
- 不用：用户还在 onboarding、尚未体验任何价值 → 用 L8-04 新手引导 先到 aha moment；此时弹墙会毁掉激活与留存。
- 必检：确认付费墙只在 aha moment 之后触发，且没有在 onboarding、打字 / 播放 / 提交中途弹出（反模式项：mid-flow 模态）。
### L8-16 feature-comparison
- 判断：把「已经决定要买、正在核对哪一项包含什么」的人，用最少的行看清**真正决定选择的差异**，而不是把整张规格表丢给他自己拼答案。
- 不用：用户还在发现 / 浏览候选，没进入权衡 → 用 L6-05 卡片网格 或结果列表；对比表只用于已收窄的短名单。
- 必检：明确「在比较什么、哪 3–4 条属性决定选择」，并把它们置顶；其余收进「显示全部差异」。
### L8-17 faq-page
- 判断：让带着一个具体问题来的人，在 30 秒内找到**用他自己的话写的**、可直接照做的答案；答案没找到时，清楚地知道下一步找谁。
- 不用：一个问题需要多段 / 截图 / 完整流程才能说清 → 用独立教程 / 帮助文章，FAQ 只留一行答案 + 链接（NN/g 判断法）。
- 必检：检查问题来自近 90 天真实工单 / 搜索词，用客户原话，未臆造关键词问题；10–30 题量级且季度复盘（反模式项：过期条目 / 100+ 平铺）。
### L8-18 form-page
- 判断：让「只想问一件事 / 提交一次申请」的人用最少字段成功送达，并**确切知道发生了什么、接下来会怎样**，即使中途出错也不重写一遍。
- 不用：>5–6 字段、有分支或需跨会话保存 → 用 L8-13 多步表单：进度、逐步校验、草稿与中断恢复。
- 必检：联系表单示例为姓名 / 邮箱 / 留言，每个字段都能回答「谁用它回复、能否稍后获得」；其他申请按业务所需字段，不套用这三个基线。>5–6 字段改评估多步表单。
### L7-01 accordion-collapse
- 判断：把一组**同层级、可独立收起**的内容压成「标题列表」，让用户先扫标题、再按需展开，从而减少长页滚动；但绝不把完成任务必需的内容藏进折叠。
- 不用：完成任务**必需**的内容（必填字段、错误提示、价格 / 条款、确认信息） → 直接常显在页面上；关键内容不得藏进折叠（Byteion、subux.pro、CANON 一致：「Do not hide critical form inputs / required fields」）
- 必检：检查每个触发是**真 `<button>`**（或 `<summary>`）且被 `<h2>–<h6>` 包裹、整行可点，不是 `<div onClick>`。
### L7-02 disclosure
- 判断：用**一个**真按钮在原地显隐**一块**可选补充内容，不改变页面上下文、不跳路由、不开浮层；关键任务信息永远留在主要内容里。
- 不用：完成任务 / **做对决策必需**的信息（资格条件、费用、警告、错误、后果、必填字段） → 直接常显在主要内容里；uxpatternsguide 明确「Do not use progressive disclosure as a hiding place for information that is critical to the user's task」，iThome「会影响决策的必要规则不应只躲在 Disclosure 里」。
- 必检：检查触发是**真 `<button>`**（或 `<summary>`）而非 `<div onClick>`；`aria-expanded` 放在按钮上并随开合实时翻转、无 stale 值。
### L7-03 inline-editing
- 判断：让一个**已显示的值**在原位置直接变成输入框，用户不离开页面、不丢上下文就完成一次低风险单值修改；它是「阅读态 ↔ 编辑态」两种模式共用一个盒子的容器。
- 不用：**不可逆 / 高影响 / 批量 / 跨记录**的改动（删除、退款、角色权限、对外发布、金额结算、库存扣减） → L4-03 确认对话框 或 L8-10 详情页 走提交前审阅；xyui 明确「它适合改数值，不适合做决定」
- 必检：检查展示态编辑触发是**真可聚焦按钮**并带具名 `aria-label`，可编辑性常显而非 hover-only；Tab/Enter/F2 能进入编辑。
### L7-04 master-detail
- 判断：用一个列表（主 / index）驱动一块详情（从 / detail），宽屏并排对照、窄屏降级为「列表页 ↔ 详情路由页」；核心不是「两栏」，而是**一个选中项拥有详情**的关系与跨断点导航状态保持。
- 不用：**没有稳定选中项**（详情脱离列表就无意义 / 集合无选中概念） → Feed 网格（M3）或单列 L6-03 列表；uxpatternsguide「Avoid master-detail when no stable selected item exists」
- 必检：检查宽屏是「列表 + 选中项 + 详情」三者同时可见，无选中时 detail 有明确 `empty-detail` 而非空白半屏。
### L7-05 split-pane-inspector
- 判断：把工作区切成两块（或三块）常驻 pane，用一条**可拖动、可键盘操作**的分隔条分配空间；核心是「边界可调」这个控件，而不只是「两栏并排」。
- 不用：只是**静态**分隔线（分组、不可调） → L1-12 Divider / Separator；**不要给它 tabindex 或 role=separator 的可聚焦语义**
- 必检：检查可调分隔条是 `role="separator"` + `tabindex="0"`，带 `aria-valuenow` / `aria-valuemin` / `aria-valuemax`、`aria-valuetext`、`aria-controls`→primary pane、具名 `aria-label`；用方向键调整，且**没有**把 `aria-expanded` 误当作分隔条语义。
### L7-06 panel-pane
- 判断：Pane 是「窗口自身空间的一块划分、承载一个目的地（destination）」，Panel 是对任意盒状区域的宽松叫法；本条讲**如何用容器把内容分组、以及这些容器在断点上如何进出**。
- 不用：把**关键内容**（必填字段、错误、主操作、价格/条款）收进可隐藏的 pane → 常显在默认 pane；pane 可进出，但完成任务必需的信息不能随 pane 一起消失
- 必检：检查每个 pane 是命名 region（`section` + `aria-label`/`aria-labelledby`），不是一堆无名 `div`。
### L7-07 page-container
- 判断：页面级的**内容宽度约束 wrapper**——用 `max-width` + 自动居中 + 响应式 gutters 把内容限制在舒适可读的宽度内，让主要区块共享同一条对齐线。
- 不用：卡片 / 表单字段**内部**的小间距 → 用 `padding`（如 `p-6`）或 Stack，不用 Container（Byteion Common mistakes）
- 必检：检查每个页面 / 主要布局区域**只有一个** Container，没有嵌套两个带 gutter 的 Container。
### L7-08 fieldset
- 判断：用原生 `<fieldset>` + 首个子元素 `<legend>` 给**一组相关表单控件**建立语义分组与可访问组名，让读屏在每个选项前先播报「这组是在选什么」。
- 不用：**单个**文本输入且已有自己的 `<label>` → 不需要 fieldset——单个 label 已提供 accessible name，fieldset **不增加价值**（W3C H71、sendform）；用 L2-06 Label / H44
- 必检：检查每组相关控件包在 `<fieldset>` 内，且 `<legend>` 是**第一个子元素**、文案描述了「这组在选什么」。
### L7-09 progressive-disclosure
- 判断：**一种信息分层策略，不是一个组件**——先给出多数人当下要用的少量选项，把高级 / 罕见内容放在「一个明确动作之外」，让复杂度在被请求时才出现，从而降低认知负荷而不削减能力。
- 不用：把**高频**功能藏进「Advanced」只为首屏好看 → 升到 Level 1 常显。ZOOZ 的判据：若功能被 30% 用户使用，把它藏进 Advanced 不是渐进披露，而是让 30% 用户去找它。
- 必检：检查已用任务分析 / 使用数据 / 观察式测试决定 Level 1 与 Level 2 的分层，而不是「看起来干净」。
### L7-10 truncation-read-more
- 判断：把一段长文本按**行**裁到 N 行，配一个真按钮「Show more / Show less」就地展开 / 收起同一段的剩余文字；控制的是**长度**而非内容秘密。
- 不用：文本含**法律条款 / 价格 / 日期 / 错误信息 / 表单说明 / 产品限制 / 资格条件 / 否定词 / 总额 / 截止时间** → 默认全显或重做信息层级；techbloat 的判据：凡会改变文本含义的内容都不做行截断，包括条款、价格、日期、错误、限制、否定与截止时间。
- 必检：检查按**行** clamp 且先测 `scrollHeight > clientHeight`，未溢出时**不渲染** Show more。
### L7-11 sticky-affix
- 判断：`position: sticky` 让元素**先留在文档流里、滚动到阈值才钉住、并受父容器边界约束**，从而在长内容里保持方位感；代价是它会占用视口高度并可能遮挡内容、锚点与键盘焦点。
- 不用：元素属于**整个 viewport**、必须一直固定（cookie 条、全局底部导航、聊天挂件、FAB、Modal） → `position: fixed`，并**为它预留空间**（body padding / 安全区）
- 必检：检查按「属于 section → sticky / 属于 viewport → fixed」选型，fixed 已为它预留空间、sticky 有至少一个 `top/bottom/left/right` inset。

## 工程常见但原库未覆盖（外部补充，证据等级 B/D）

### 批量操作栏（Bulk Action Bar）
- 判断：列表 / 表格支持多选且选中后要批量处理 → 顶部或底部批量栏。
- 不用：单条操作也放批量栏；选中后遮挡内容或顶掉分页。
- 必检：显示已选数量；提供全选 / 清除；破坏性批量操作走二次确认；`HR-09`。

### Cookie 同意 / 隐私横幅
- 判断：需要合规告知且用户可配置 → 底部或侧边同意条；仅告知 → 页内 Banner。
- 不用：阻断首屏且不给「拒绝」；把同意做成默认勾选。
- 必检：拒绝与同意同等可见；可随时更改；不因拒绝而核心功能不可用。

### 聊天 / 会话界面
- 判断：多轮异步沟通 → 会话列表 + 消息流 + 输入区；单次问答 → 表单或搜索。
- 不用：消息流无时间分组；输入区无草稿与失败重试。
- 必检：新消息不抢焦点；滚动位置保持；`aria-live` 播报（`HR-10`）；发送失败可重试。

### Markdown 编辑器 / 聊天输入（Composer）
- 判断：结构化长文本 → Markdown 编辑器 + 预览；短消息 + 附件 → 聊天输入。
- 不用：纯文本场景塞富文本工具栏；不可撤销的长内容直接发送。
- 必检：快捷键不劫持系统键；`HR-09`；发送失败可重试；草稿保护。

## 业务任务模式（能力扩充 v1.2.0 复审修订）

> 用户指定扩充，属过程归纳（证据等级 D），不是原库 226 篇的结论；与上面条目并列使用，不覆盖已裁定基线。

### 分次办理与提交前复核（Task Checklist / Multi-step Form / Review & Submit）
- 什么时候该想到它：事项可以分次、独立完成 → 带状态的任务清单；流程必须按顺序推进 → 多步表单（强顺序本质是状态机，配步骤门禁与断点续办）；提交前需要集中核对并能返回对应项修改 → 复核页（Review & Submit）。需要他人签字时转审批工作流，不在这里另造审批环节。
- 哪些条件会改变选型：子任务是否互相依赖、是否允许跳到未完成项；字段数与分支、是否需要跨会话草稿；是否有高风险或不可逆后果；是否由他人做决定；是否需要服务端校验前置状态防绕过。独立无依赖 → 任务清单；强顺序有条件分支 → 多步表单；提交前核对 → 复核页；他人决定 → 审批工作流（L8-14）。
- 最容易漏掉的行为：任务清单要显示完成状态与剩余项，允许跳转；多步表单要保存草稿、显示进度，返回不丢已填内容；**只禁用前置条件未满足的步骤，当前可填写步骤保持可用，续办时恢复到当前可办理步骤**，服务端同步校验防绕过；复核页每项能直达对应字段，改完回到复核位置，最终确认前显示完整摘要与遗漏必填；不能把关键确认藏进折叠。
- 用什么场景验收：月度报销含 5 项材料，1、2 项可分别补齐，第 3 项依赖第 1 项，提交前要核对金额与票据。验收能否组合任务清单、多步表单和复核页；第 2 项已可填时不得禁用，只有第 3 项在第 1 项未完成时禁用；隔天回来直接恢复到第 2 项，并能从复核跳回第 3 项再回到原位置。

### 变化与追溯（Activity Feed / Audit Log / Version Diff）
- 什么时候该想到它：用户问「最近发生了什么」→ 活动动态；「谁在何时做了什么」→ 审计日志；「具体改了哪些值」→ 版本差异。三者回答不同问题，不能互相替代。
- 哪些条件会改变选型：是否只要最新摘要，还是要穷尽、不可变、可搜索导出并保留 IP/actor 与保留策略；是否需要字段级前后值对比。追近况用动态；合规取证用审计日志；对比两个版本用差异视图；涉及他人签字或状态推进时走审批工作流（L8-14）。
- 最容易漏掉的行为：活动动态没有稳定事件 ID 与不可变存储时不能当证据；审计日志要只读、按时间/操作者/对象过滤并保留策略；版本差异要标出字段名、前值、后值、修改人与时间，不能只写「已更新」；空/加载/失败三态都要出稿。
- 用什么场景验收：客户投诉金额被改，运营想同时看最近动态、谁改的、改了哪几个字段。验收能否分别给出动态流、只读审计条目和字段级差异，且审计条目不可编辑、差异含前值后值与时间。
